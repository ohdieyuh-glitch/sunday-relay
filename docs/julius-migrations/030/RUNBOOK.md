# Migration 030 on the LIVE Julius database: runbook (founder gates, 2026-10-02)

Migration `030_julius_outbox_event_no_reread` drops ONE foreign key, `relay_wonderland.outbox.outbox_event_id_fkey` (outbox.event_id → events.event_id ON DELETE CASCADE). That key's check was the second source of the row 13 (i) serialization failures.

The guarantee the key gave is kept by triggers that read no relation:
- an outbox row only for an event written earlier in the same transaction;
- event and outbox ids immutable;
- deletes cascade;
- a TRUNCATE of events is refused.

**Founder gates:**
- drop only this key;
- prove zero orphans first;
- record the constraint and the counts;
- back up, with a restore path;
- STOP if integrity is already violated;
- re-verify after;
- drop no other constraint.

**If any step below fails, STOP THE DEPLOY.**

## FIRST: classify the store (added 2026-10-03, founder path R1)

This runbook first assumed a store populated through 029. On 2026-10-03 the founder's live pre-deploy refused because that was false: the workstation `julius` database had **never been initialized** (no schema, no ledger, no tables), and it failed only through an SQL error, not by design.

So every deploy now starts by classifying the store, read-only, with `classify-store.sql`. It has 11 ordered rules, is total, and runs BEFORE any table-specific query:

| State | What it means | Path |
|---|---|---|
| `EMPTY` (rule 4) | no relay_wonderland, no ledger, public only and holding nothing | **The EMPTY path** below: a first-time bootstrap through the whole chain |
| `AT_029` (rule 6) | the ledger is exactly accepted main's versions | **Steps 0–6** below, unchanged |
| `AT_TARGET` (rule 7) | 030 already applied | STOP: nothing to deploy |
| `PARTIAL` (rule 9) | a strict prefix of the chain: what a failed bootstrap leaves | STOP. The only recovery is rollback (d), under its conditions |
| `UNEXPECTED` (rules 1–3, 5, 8, 10, 11) | an extension, an event trigger, another schema, an object in public, relay_wonderland without a ledger, an empty ledger, a gap, an unknown version | STOP. The reason is named; investigate |

```
docker exec -i julius-postgres psql -U julius -d julius -v want_029=<…> -v want_030=<…> < docs/julius-migrations/030/classify-store.sql
```
- `want_029` and `want_030` are the stamped versions of accepted main and of this head, generated by command from the checkout, never typed.
- Rules 6, 7 and 9 rely on the chain's order being its filename order. The bootstrap driver refuses unless every loaded migration is its file, entry for entry.

**The inherited URL (founder ruling R-6, 2026-10-03).**
- Before landing, the founder parks the user-level `DATABASE_URL` that names this store under the deployment-only `JULIUS_LIVE_STORE_URL`.
- Deployment tools read only that parked name, and REFUSE while `DATABASE_URL` or `JULIUS_DATABASE_URL` is PRESENT AT ALL, whatever it names, in the Process, User or Machine scope. They record that state (variable names and host:port/db only, never a secret).
- Shells and processes started before the rename keep their old copy, so they stay stopped.
- `DATABASE_URL` is restored intentionally only after the bootstrap (or apply) record has been verified by Second; Julius processes then restart cleanly.

## ORDER: steps 0–2 happen BEFORE the PR is landed

Landing changes nothing in the local container by itself. But every entry point of a checkout that CONTAINS 030 (this branch, its PR, the landed main) migrates the database its environment names, and every workstation shell inherits the LIVE `DATABASE_URL`. These eight all call `migrate()` when they start:
- `relay-bridge/julius-live-mission.ts`;
- `scripts/julius-live-preflight.ts`, the zero-dispatch preflight (`npm run relay:julius:preflight`), through `migrateIfNeeded`;
- `scripts/julius-live-preflight-identity.ts`;
- `scripts/julius-recovery-drill.ts`;
- `scripts/julius-failure-recovery-drill.ts`;
- `scripts/julius-repair-loop-drill.ts`;
- `scripts/julius-sibling-support.ts`;
- `scripts/project-brain-proof-main.ts`.

So the first local run of any of them, from such a checkout, would apply 030 to the live store BEFORE a backup and a recorded pre-check existed. 030's own guard would still keep integrity, but the founder's order would be broken. Therefore:
1. **Until step 3 is recorded, from ANY checkout that contains 030:** run none of those entry points against the live store. Any local run sets BOTH `JULIUS_DATABASE_URL` and `DATABASE_URL` to a throwaway database (or unsets them). The test suites already read only `JULIUS_TEST_DATABASE_URL`.
2. **Before landing:** step 0 (quiesce), step 1 (verified backup, sha256 recorded), step 2 (pre-check recorded). The founder's landing block refuses unless the backup's `.sha256` file and the pre-check record exist at the paths it is given.
3. **The writers stay stopped from step 0 until step 6.** If they must run again before step 3 (for example, the landing slips), redo steps 1 and 2 before step 3, so the counts the post-check compares are the ones the migration met.
4. **Step 3** applies 030 explicitly (the `psql` path below), and its record is kept. Only then may the bridge, the mission job or the scripts run against the live store again.

## The live store

- **What it is:** the Docker container `julius-postgres` on the workstation, published on `127.0.0.1:5432`, database `julius`, role `julius`.
  - Until the R-6 rename, every workstation shell's inherited `DATABASE_URL` pointed here.
- **What it held on 2026-10-03: nothing.**
  - Read-only inspection found the `julius` database EMPTY (never initialized), and Second Julius confirmed it.
  - The same cluster's earlier volume (`julius-postgres-anon-old`, inspected read-only on a copy) held no Julius state either.
  - The Julius tables on this server live only in test, drill and seam databases.
  - Earlier text calling this "the live store" with real mission history was never measured, and it was wrong.
- **What it is not:** the paid mission job's database. That job runs on a fresh GitHub-hosted `ubuntu-24.04` runner, where `.github/julius-live-executor.sh` starts its own container, also named `julius-postgres`, with no volume. It is created empty for each run, so the chain applies there to an empty store and needs no runbook. This workstation container is the only persistent Julius store.
- **Confirm before anything else:** `docker ps --filter name=julius-postgres`, then `docker exec julius-postgres psql -U julius -d julius -c "SELECT current_database(), current_user, version();"`, then **classify it** (above).
- **Never point a test at this database.**
  - Tests read `JULIUS_TEST_DATABASE_URL` only.
  - The real-PostgreSQL evidence in step 5 runs on throwaway databases.

## Steps

**0. Quiesce the writers.** Stop the bridge and any mission job that writes this store. The counts in steps 2 and 4 must be comparable ("no lost writes").

**1. Back up and verify.** Do not continue without a verified dump.
```
docker exec julius-postgres pg_dump -U julius -d julius -Fc -f /tmp/julius-pre-030.dump
docker exec julius-postgres pg_restore --list /tmp/julius-pre-030.dump > julius-pre-030.toc   # must list relay_wonderland objects
docker cp julius-postgres:/tmp/julius-pre-030.dump <backup-dir>/julius-pre-030-<UTC>.dump
sha256sum <backup-dir>/julius-pre-030-<UTC>.dump > <backup-dir>/julius-pre-030-<UTC>.dump.sha256
```

**2. Pre-check (read-only). Save the output.**
```
docker exec -i julius-postgres psql -U julius -d julius < docs/julius-migrations/030/precheck.sql > precheck-<UTC>.txt
```
STOP unless:
- `fk_matches = t`;
- `orphan_outbox_rows = 0`;
- `migration_029_applied = t`;
- `migration_030_applied = f`.

**3. Apply 030, explicitly (after landing, before any entry point of the new main touches the live store):**
```
docker exec -i julius-postgres psql -U julius -d julius -v ON_ERROR_STOP=1 < src/relay/persistence/wonderland-migrations/030_julius_outbox_event_no_reread.sql > apply-030-<UTC>.txt 2>&1; echo "exit $?" >> apply-030-<UTC>.txt
```
- `exit 0` is required. Any other exit means 030 refused or failed and rolled back: rollback (a).
- The migration checks itself inside its one transaction.
  - It raises `migration_030_refused` (and drops NOTHING) unless the key is exactly the one described above and no orphan exists.
  - It raises `migration_030_postcheck` if, after the drop, the key remains or an orphan appears.
- Keep its `NOTICE migration_030_precheck: …` line, which carries the counts, with the deploy record.

**4. Post-check (read-only). Compare it with step 2.**
```
docker exec -i julius-postgres psql -U julius -d julius < docs/julius-migrations/030/postcheck.sql > postcheck-<UTC>.txt
```
PASS only if all of these hold:
- `fk_present = f`;
- the constraint listing equals step 2's minus exactly `outbox_event_id_fkey` (gate F);
- the trigger listing adds exactly `events_written_remember`, `outbox_requires_event_written`, `events_event_id_immutable`, `outbox_event_id_immutable`, `outbox_follows_event_delete` and `events_truncate_refused`;
- `orphan_outbox_rows = 0`;
- `events_rows` and `outbox_rows` equal step 2's;
- `migration_030_applied = t`.

**5. Rerun the evidence. NOT on this database.**
- The real-PostgreSQL settlement and concurrency suites (`julius-event-append-contention`, `julius-event-append`, `julius-handoff-fence`, `julius-handed-recovery`, `julius-multi-mission`, `julius-live-preflight-identity`) on the deployed commit, in julius-real-infra CI and/or on the portable throwaway server.

**6. Restart the writers.** Watch the first appends for a `23503 outbox_event_not_written` or `outbox_event_id_malformed`. Either would mean a writer outside the five pinned ones, so STOP.

## The EMPTY path: a first-time bootstrap (founder path R1, 2026-10-03)

Use it only when the store classifies `EMPTY`. No ordinary entry point may initialize the store; only this reviewed transition does (founder ruling: no implicit auto-migration).

**E0. Quiesce and park.**
- Every Julius writer is stopped, the Julius Connect dev service included.
- `DATABASE_URL` is parked as `JULIUS_LIVE_STORE_URL` (R-6).
- Writers stay stopped from here until E6.

**E1. Back up and record, before landing.**
- The pre-deploy classifies the store EMPTY and records:
  - the classifier line;
  - the EMPTY catalog fingerprint (`fingerprint-store.sql`);
  - the cluster's `system_identifier`;
  - the container and image ids;
  - the role and tablespace lists.
- It still takes a backup: `pg_dump -Fc` of the empty database. Its table of contents must list NO relay_wonderland object, and its restore into a throwaway container must classify EMPTY with an equal fingerprint.

**E2. Land.** Exactly as for the populated path: the founder's landing block reads the E1 record.

**E3. Bootstrap, after landing and before ANY entry point of the new main runs.**
- The wrapper re-checks, at its start:
  - the classifier says EMPTY and the fingerprint equals E1's;
  - the same `system_identifier`, container and image;
  - no other session, no writer process, and neither `DATABASE_URL` nor `JULIUS_DATABASE_URL` present in any scope;
  - the checkout is the landed head, clean.
- Then it runs the driver from the checkout root:
  ```
  npx esbuild scripts/julius-bootstrap-empty-store.ts --bundle --platform=node --format=cjs --outfile=dist-relay-bridge/julius-bootstrap-empty-store.cjs --external:pg
  node dist-relay-bridge/julius-bootstrap-empty-store.cjs --expect-database julius --expect-system-identifier <id>
  ```
  - The target comes only in `JULIUS_BOOTSTRAP_DATABASE_URL`, set by the wrapper from `JULIUS_LIVE_STORE_URL`.
  - `DATABASE_URL` and `JULIUS_DATABASE_URL` are unset for the process; the driver refuses otherwise.
- What the driver does:
  - checks every loaded migration is the checkout's file (count, stamp = filename, bytes);
  - re-checks identity, the other sessions and EMPTY in its own session;
  - applies the chain through `migrateIfNeeded`, never hand-written SQL;
  - reads the ledger back by `applied_at`, and it must be the build's exact order.
- **The wrapper also compares the driver's `LOADED` hashes with the landed head's blobs**, so a modified tree can never run here.
- Exit codes:
  - exit 0 with `BOOTSTRAP OK` is the ONLY success;
  - exit 2 `BOOTSTRAP FAILED … PARTIAL and is not initialized` means go to rollback (d);
  - exit 3 or 4 means nothing was written.

**E4. Post-check (read-only).** PASS only if all of these hold:
- the ledger holds the build's versions in order (the driver's `LEDGER` lines);
- the catalog fingerprint equals the reference the targeted rehearsal built from the same head by an independent method (psql applying the files in order);
- `rowcounts-store.sql` equals that reference line for line;
- `postcheck.sql` shows `fk_present = f`, the six 030 triggers and 0 orphans;
- the classifier says `AT_TARGET`.

**E5. Verify.** Second Julius verifies the bootstrap record. Only then does the founder restore `DATABASE_URL` intentionally.

**E6. Restart** the Julius processes cleanly. The zero-dispatch preflight runs with explicit URLs, and its `migrateIfNeeded` must report nothing applied.

## Rollback

**(d) A first-time bootstrap FAILED (founder rulings R-5, 2026-10-03, and the R1 unblock).**
- `DROP SCHEMA relay_wonderland CASCADE` is the approved rollback ONLY for that case, ONLY through the reviewed founder procedure, never ad hoc.
- It is allowed ONLY when all of these are proven:
  - the store was verified EMPTY immediately before the bootstrap;
  - every object the chain created is inside relay_wonderland;
  - no migration-created extension or external object exists;
  - no unrelated schema or object was modified;
  - the bootstrap failed before any normal Julius workload was allowed;
  - the rollback path already passed the targeted throwaway rehearsal;
  - after the drop the classifier reports the exact original EMPTY state;
  - the pre-bootstrap and post-rollback EMPTY fingerprints match.
- It runs only through the reviewed founder wrapper, which proves each precondition or STOPs naming it:
  - the bootstrap record says FAILED and carries the pre-bootstrap EMPTY fingerprint;
  - the classifier reads PARTIAL with rules 1–3 clean;
  - no writer, session or preflight has run since;
  - the rehearsal's case F verdict is pinned.
- `rollback-bootstrap.sql` runs it as ONE transaction:
  - it STOPs, dropping nothing, if relay_wonderland is absent, an event trigger or an extension exists, or anything outside relay_wonderland fingerprints differently from E1's EMPTY store;
  - it then drops the schema and recomputes the fingerprint;
  - it COMMITs only if that fingerprint equals E1's; otherwise it rolls back, which undoes the drop, and STOPs.
  ```
  docker exec -i julius-postgres psql -U julius -d julius -v expected_empty=<E1 fingerprint sha256> < docs/julius-migrations/030/rollback-bootstrap.sql
  ```
- Exit 0 with `ROLLBACK DONE` is the only success. After it, the classifier must say `EMPTY` (rule 4).
- **If any assumption is false or ambiguous: STOP instead of dropping the schema.**

**(a) 030 refused in step 3.** Nothing changed (one transaction). Investigate; do not retry until step 2 passes.

**(b) The post-check fails, or a decision reverses the change.**
```
docker exec -i julius-postgres psql -U julius -d julius < docs/julius-migrations/030/down.sql
```
- It restores the identical foreign key, removes 030's triggers and functions, and deletes the stamp, in one transaction.
- It refuses, changing nothing, if an orphan exists.
- **Then deploy code that no longer lists 030;** otherwise the next `migrate()` re-applies it.
- Re-run step 2's check: the constraint listing must equal the original pre-check's.

**(c) Last resort: restore the backup.** Restore into a NEW database first and inspect it before replacing anything:
```
docker exec julius-postgres createdb -U julius julius_restore_030
docker exec julius-postgres pg_restore -U julius -d julius_restore_030 /tmp/julius-pre-030.dump
```
- Then repoint the runtime (`JULIUS_DATABASE_URL`) at it, or rename the databases while the writers are stopped.
- Do not `pg_restore --clean` over the live database without the founder.
